1. Introduction

Caliptra was announced in 2022, and after a period where only the spec and code existed, 2026 is when chips that actually integrate Caliptra are starting to show up in the real market. That means we're entering an era where GPUs, SSDs, NICs, and other datacenter devices come with a "root of trust baked into the die" as standard equipment. So I think now is a good time to write this technology up.

Looking at where it's actually being deployed makes the momentum feel more real.

  • Microsoft & Google mandates: both companies now require Caliptra-based RoT in every compute, networking, and storage controller chip supplied into their datacenters. It's effectively being forced across the entire supply chain.
  • Google's first-party silicon: Google is integrating Caliptra into its own custom CPU/GPU/DPU/BMC/SSD chips, and requiring the same from external suppliers.
  • Storage controllers: SSD controller vendors like ScaleFlux have announced adoption. This area naturally dovetails with OCP L.O.C.K. (SED key management), covered later.
  • Microsoft Azure infrastructure: Microsoft is folding Caliptra 2.0/2.1, including Adams Bridge (PQC), into its infrastructure security architecture.

For reference, NVIDIA and AMD are founding members, but there isn't much officially published detail on which specific production products (e.g., which GPU generation) shipped with which version, so I won't make claims about that here.

This post covers:

  • Caliptra's relationship with OCP (who defines the spec, who implements it)
  • The background behind Caliptra's creation and its version history (1.0 → 2.0 → 2.1)
  • Its full hardware/software architecture as it stands today
  • A point-by-point comparison with ARM RSE

2. Caliptra's Relationship with OCP

To really understand Caliptra, you first need to know where it came from. The short answer: Caliptra is the result of a requirement set by a consortium called OCP. So this section starts with what OCP is, then covers why OCP and Caliptra are linked, and finally the governance structure that splits the spec from the implementation.

What OCP Is

OCP (Open Compute Project) is an open hardware consortium founded in 2011, led by Facebook (now Meta). It's where datacenter hardware designs — servers, racks, networking, storage — get published and standardized. Meta, Microsoft, Google, Intel, AMD, and NVIDIA are among its members, and it's also the venue where hyperscalers jointly define requirements like "this is what the hardware we buy needs to look like."

It shares a lot of members with DMTF, but the roles differ. In short: DMTF defines protocol standards (SPDM, MCTP, PLDM), while OCP defines hardware design and security requirements.

What the OCP Security Group Produces

DeliverableRole

Attestation Spec v1.0Attestation requirements for datacenter devices. Adopts DMTF SPDM as the attestation protocol.

CaliptraA silicon RoT integrated into the die itself. The subject of this post.

Why OCP and Caliptra Are Linked

Looking at just the table above, Caliptra might seem like just one of OCP's many deliverables. The relationship is actually more direct than that. In short: Caliptra is the concrete answer to a requirement OCP created.

Tracing the flow:

  • Defining the requirement: hyperscalers established, within OCP, the direction that "every chip entering a datacenter must have a verifiable root of trust inside the die." The Attestation Spec and Project Cerberus are what turned that requirement into documents.
  • Defining the implementation: requirements alone don't produce a chip. So a concrete implementation — "an open-source silicon RoT integrated into the die" — was defined, and that's Caliptra.
  • Spec management: Caliptra's "Silicon RoT Services" spec is owned and revised by the OCP Security group. In other words, Caliptra is formally part of OCP's standards track.
  • Exposing attestation results: the measurements and signatures Caliptra produces are delivered to the platform via SPDM, which the OCP Attestation Spec adopted. The producer (Caliptra) and the delivery protocol (OCP-adopted SPDM) mesh together within one ecosystem.

To sum up: OCP is the venue that decides "what's needed" (requirements/standards), and Caliptra is the answer to "so what goes inside the chip" (implementation). That's why this post covers OCP alongside Caliptra.

Dual Governance: OCP Owns the Spec, CHIPS Alliance Owns the Implementation

There's one more layer here. Personally, I find the split governance the most distinctive part of Caliptra.

  • Spec (requirements): managed by the OCP Security group. Defines the "Silicon RoT Services" a datacenter SoC must provide.
  • Implementation (RTL + firmware): managed by CHIPS Alliance, under the Linux Foundation. Develops the SystemVerilog RTL and Rust firmware as open source.
┌──────────────────────────┐    adopts SPDM as      ┌──────────────────────┐
│ OCP                      │    attestation proto   │ DMTF                 │
│  · Caliptra Spec         │ ─────────────────────> │  · SPDM (DSP0274)    │
│  · Attestation Spec v1.0 │                        │  · MCTP / PLDM       │
│  · Project Cerberus      │                        └──────────────────────┘
│  · S.A.F.E. / L.O.C.K.   │
└────────────┬─────────────┘
             │  specification

To put it simply: OCP draws the blueprint, and CHIPS Alliance embodies it. OCP's spec defines "what" to build; CHIPS Alliance turns that into working RTL and firmware code that defines "how."

One thing worth noting: both of these are governance bodies (who manages and revises), not the ones actually manufacturing chips. The blueprint (OCP) and the reference implementation (CHIPS Alliance) are both open source, and chip vendors like AMD, NVIDIA, and Google take them and integrate/mass-produce them into their own SoCs. Here's the full chain:

OCP blueprint (spec)
  └─> CHIPS Alliance reference implementation (RTL + Rust FW)
        └─> chip vendors integrate/customize into their own die
              └─> production chips (GPU / SSD / NIC / CPU ...)

This structure — spec open, implementation open — is Caliptra's core strength: vendors can take it for free, and modify it if they need to.

Cerberus vs. Caliptra: Division of Labor

Both are OCP RoTs, but they sit in different places. Cerberus is board-level (a separate chip that verifies a platform's entire firmware), while Caliptra is inside the die (each SoC/ASIC's own measurement and identity). In a datacenter platform, the two coexist: think of a Cerberus-style platform RoT acting as the SPDM Requester, collecting the measurements backed by the Caliptra inside each device.

3. Caliptra History

Background: The Limits of External RoTs

A TPM or a separate RoT chip (including Cerberus) is a component outside the package. That created clear limitations:

  • Interposer attacks: exposed to physical attacks that intercept signals between the chip and the board.
  • Vendor fragmentation: every device implements RoT differently, which is expensive for hyperscalers to validate.
  • Opacity: closed firmware makes auditing impossible.

Hyperscalers reached a clear conclusion: put the root of trust inside the die, and open-source the entire design.

Timeline

PeriodEvent
2022.10Announced at the OCP Global Summit: a joint effort by Google, Microsoft, AMD, and NVIDIA
2023Caliptra 1.0: an RTM (RoT for Measurement) core — DICE identity, measured boot, a signing oracle
2024–25Caliptra 2.0: PQC introduced (Adams Bridge, ML-DSA), Subsystem mode, streaming boot, ownership transfer
2025–26Caliptra 2.1: Adams Bridge 2.0 (ML-DSA + ML-KEM, hardened side-channel resistance), OCP L.O.C.K. key management implemented
2026Chips integrating Caliptra begin appearing on the market

Why PQC Was Adopted Early

The most striking decision in Caliptra 2.x is building post-quantum cryptography (PQC) in as a hardware accelerator (Adams Bridge). The motivation is the "harvest now, decrypt later" attack model — collect ciphertext now, decrypt it once quantum computers exist. Since a chip stays in the field for close to a decade after it ships, the calculation is that a chip manufactured in 2026 needs PQC built in now to stay safe for its whole lifecycle. It supports both NIST standards: ML-DSA (signatures) and ML-KEM (key encapsulation).

Building Trust

Being open source isn't the end of the story — what's striking is the layers of verification that openness makes possible:

  • Cross-review by the security teams of member companies (MS/Google/AMD/NVIDIA)
  • Third-party audit under OCP S.A.F.E. certification
  • Formal verification by outside vendors
  • The entire firmware written in Rust for memory safety

4. Caliptra Hardware Architecture (as of 2.x)

Overall Block Diagram

│                                       └──────────────┘  └─────────────────┘  │
│  ┌──────────────────────────────────────────────────────────────────────┐   │

│  └──────────────────────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────────────────┘

Here are the key components:

  • VeeR EL2: an RV32IMC RISC-V core. A verified open-source core from CHIPS Alliance that runs only Caliptra's own firmware.
  • ICCM/DCCM, 128KB each: tightly-coupled memory dedicated to instructions/data. Only firmware verified by the ROM gets loaded into ICCM.
  • Crypto engines: classic algorithms like SHA, HMAC, AES, and ECC P-384, plus the Adams Bridge PQC accelerator starting in 2.x (covered separately below).
  • Key Vault / PCR Vault / Data Vault: personally, I think this is the crown jewel of Caliptra's design. Not even the CPU can read key material in plaintext — keys only flow between vault slots and engines. Even if the firmware is fully compromised, key material never leaks.
  • Fuse interface: supplies the UDS (Unique Device Secret) and Field Entropy from fuses. The UDS is the root of every identity.
  • Mailbox: the sole channel through which the SoC sends commands to Caliptra (registering measurements, requesting signatures, etc.).

Adams Bridge: the PQC Hardware Accelerator

Adams Bridge is the dedicated post-quantum cryptography (PQC) accelerator built into Caliptra 2.x. It was co-developed by AMD, Google, Microsoft, and NVIDIA, with the RTL also released publicly.

The name's origin is a fun one — it's a metaphor for a "bridge" spanning the huge gap between classical asymmetric cryptography (RSA/ECC) and post-quantum cryptography. It's named after the mythical land bridge connecting two landmasses (Adam's Bridge), a name given by Microsoft (Azure).
  • Unified datapath: processes the NIST-standard ML-DSA-87 (FIPS 204, signatures) and ML-KEM-1024 (FIPS 203, key encapsulation) in a single hardware block. It's designed to share the NTT/INTT (polynomial transform) and Keccak cores that both algorithms use, reducing area.
  • Built-in side-channel resistance: applies masking, shuffling, and constant-time control/operations. TVLA (Test Vector Leakage Assessment) testing up to 1 million traces confirmed no first-order leakage. The key goal is making sure the RoT's key-derivation operations don't leak through power or timing side channels.
  • Pipelined processing: a staged pipeline datapath streams NTT/INTT and hashing through. The reference implementation targets a 5nm process at 600MHz.
  • Versions: Adams Bridge in 2.0 was ML-DSA-focused; Adams Bridge 2.0 in 2.1 adds ML-KEM and strengthens side-channel defenses.

So why put a PQC accelerator inside the RoT at all? Because moving chip identity signing (IDevID/Alias) and firmware verification to PQC means that computation has to happen inside the RoT — fast, and side-channel safe. Handing it off to the SoC's AP would let key computation leak outside the trust boundary.

Passive Mode vs. Subsystem Mode (2.0+)

  • Passive (default in 1.x): Caliptra is an RTM handling only measurement and signing. Overall boot control stays with the existing boot chain.
  • Subsystem (2.0+): adds an MCU (manufacturer control unit), I3C, and a recovery interface to Caliptra Core, extending it into the RoT for the entire SoC. This is where features like streaming boot (receiving firmware directly from the host with no local storage) and ownership transfer come from.

5. Caliptra's Core Features

Combining the hardware blocks and firmware, the "Silicon RoT Services" Caliptra provides to an SoC ultimately break down into four groups. I'll also cover the surrounding OCP-standardized frameworks (S.A.F.E., L.O.C.K.).

1) Measured Boot

The first thing Caliptra does is measure the integrity of itself and the SoC's firmware. It accumulates the hash of each boot stage and each external firmware image into the PCR Vault. That leaves a tamper-proof record of what actually got loaded, and that measurement becomes the basis for later attestation.

2) Attestation

When a host or platform RoT asks "are you genuine, and has your firmware changed?", Caliptra answers by signing the measurements with the chip's unique identity key. That identity key is derived from the UDS (the device secret in fuses). If the firmware changes, the measurement — and therefore the signature — changes with it, so tampering can't be hidden. Starting in 2.x, it issues both an ECC P-384 signature and a PQC (ML-DSA) signature.

3) Key Management

Key management is entirely handled by the Key Vault. Not even the CPU (firmware) can read key material in plaintext; keys only flow between vault slots and crypto engines. So even if the entire firmware is compromised, the identity keys specifically never leak. Personally, I think of this as the design's last line of defense.

4) Update & Recovery

FMC/RT only update to images that pass signature verification. What's interesting here is Subsystem mode (2.0+): streaming boot (receiving firmware directly from the host with no local storage), a recovery path for restoring corrupted firmware, and even ownership transfer are all managed by the RoT.

Surrounding OCP Frameworks: S.A.F.E. and L.O.C.K.

Caliptra isn't a chip on its own — two frameworks the OCP Security group built around it pair up in real deployments.

  • OCP S.A.F.E. (Security Appraisal Framework and Enablement): a framework standardizing third-party audits of firmware/RoT implementations by accredited security assessment labs (SALs). It turns the redundant cost of every hyperscaler separately auditing vendor firmware into a structure where "one audit, everyone trusts it." It's the channel through which an open RoT like Caliptra gets objective auditing.
  • OCP L.O.C.K. (Layered Open-source Cryptographic Key-management): an open standard for self-encrypting storage (SED) key management built on top of Caliptra. The RoT manages the lifecycle (generation, sealing, unsealing) of drive encryption keys, so tampered firmware can never unlock the keys. Implemented in Caliptra 2.1.

Together, these show OCP's layering clearly: RoT inside the chip (Caliptra) → audit (S.A.F.E.) → application domain (L.O.C.K., storage) — trust extending outward.

6. Caliptra Software Architecture

The Staged Boot Chain: All Rust

Caliptra's internal firmware runs in three sequential stages: ROM → FMC → RT. Like ARM TF-A's BL1 → BL2 → BL31, this is a classic staged secure boot where each stage only loads and runs the next stage after verifying its signature. The difference: each stage accumulates the next stage's hash as a measurement, so the moment boot finishes, that becomes the basis for attestation. All three stages are written in Rust.

7. Comparison with ARM RSE

RSE in Brief

RSE (Runtime Security Engine) is a hardware RoT and isolated attestation enclave built into ARM A-profile compute subsystems (e.g., Neoverse CSS).

  • HW: a Cortex-M55 core, dedicated SRAM banks, an MPC (Memory Protection Controller), ROM
  • FW: a runtime based on TF-M (Trusted Firmware-M)
  • Services: Measured Boot, Initial/Delegated Attestation, Crypto, ADAC (Authenticated Debug Access Control)
  • In ARM CCA (Confidential Compute Architecture), it acts as the HES Host
  • In the DICE scheme, it provides a DPE (DICE Protection Environment) implementation
  • Communicates with the AP over MHU (+ the SFCP protocol)

The core idea — "an isolated security processor inside the die owns measurement, identity, and signing" — is identical to Caliptra. What differs is the ecosystem and how much is open.

Things Worth Watching

  • Same problem, two ecosystems' answers. The requirement — "isolated in-die RoT + measured boot + attestation" — is identical. But Caliptra solves it as a horizontal open standard driven by hyperscalers, while RSE solves it as IP vertically integrated into the ARM platform.
  • DICE vs. DPE: same TCG root, different layering. Caliptra implements DICE key derivation directly in its own ROM/FMC/RT chain, while RSE provides DICE layering to the outside (the AP's boot stages) as a service called DPE.
  • Not mutually exclusive. Integrating Caliptra into an ARM SoC is a real possibility. In fact, the OCP camp's actual position is closer to "ISA-agnostic — any chip entering a datacenter should have Caliptra-level RoT Services." I think a realistic future looks like an ARM server SoC with RSE, and a GPU/SSD with Caliptra embedded, mutually attesting to each other over SPDM on the same platform.

8. Wrap-up

In one line:

OCP defines the requirements (spec), CHIPS Alliance implements them as open source (RTL + Rust FW), and the result, Caliptra, signs measurements with a DICE identity.

The shift from the TPM era's "separate chip on the board" to "open-source RoT inside the die" feels like a signal that the baseline for hardware trust is moving from vendor goodwill to a verifiable, public design. Given that it ships with PQC built in from the start and is already showing up in 2026 production chips, I think it's fair to call Caliptra the de facto standard candidate for datacenter silicon security, for now.
